# Scientific API Gateway v2.0.0

Reproducible numerical experiments, reliable background tasks, and verifiable scientific artifacts.

## Compatibility and migration

This is a major release because the numerical method, units, and task response contract changed since v1.0.0. The version in package metadata, the API, and CITATION.cff is now 2.0.0.

- The reference model is `ideal-gas-ou-v1`: an exact two-dimensional Ornstein-Uhlenbeck thermostat with relaxation rate 1 and reduced units `m = k_B = 1`. Temperature and time values are in reduced units; callers using physical Kelvin or femtoseconds must supply their own justified conversion.
- `POST /api/v1/simulations/monte-carlo` returns HTTP 202 and `check_url`. Poll for `pending`, `running`, `completed`, `failed`, or `cancelled`. A task retains one `task_id`; each execution has a separate `attempt_id`.
- Inputs are strict, finite, and bounded. Unknown fields and numerically invalid inputs return HTTP 422. Work limits and admission capacity protect the service.
- Requests support `seed` (default 0) and `num_steps` (default 100). Repeated parameters and seed reproduce numerical values in the same model/runtime environment. Choose different seeds for independent replicas.
- Redis configuration uses `REDIS_URI`. A shared persistent artifact directory is required when API instances share Redis. Settings are read from environment variables and an optional `.env` file.

## Scientific reproducibility

- Local PCG64 generators, exact OU transitions, and an explicitly described terminal-snapshot temperature standard error.
- Atomic NPZ terminal states and JSON run manifests with inputs, assumptions, numerical results, model/RNG/runtime/source metadata, optional MLflow run IDs, and SHA256 checksums.
- Attempt-specific storage prevents obsolete workers from overwriting a committed result's artifacts.
- A parameterized research CLI generates plots, machine-readable data, and a checksum manifest using the same scientific implementation as the API.

## Reliable execution and observability

- Lifespan-scoped resources, bounded admission, explicit task states, and cooperative shutdown.
- A Redis backend with atomic leases, heartbeat, expired-task recovery, limited attempts, and owner-fenced result publication. Delivery is at-least-once.
- Optional OpenTelemetry propagates W3C trace context through HTTP, enqueue, execution, and worker threads; metrics cover waiting time, execution duration, task outcomes, and HTTP requests.
- Optional MLflow uses isolated clients/runs and uploads scientific artifacts while preserving failed-run status.

## Packaging, deployment, and performance

- A lightweight core and optional extras for tracking, Redis, observability, research, notebooks, benchmarks, and development.
- Reviewed `uv.lock`, pinned uv/build tooling and container image digests, portable PEP 751 export, and a correctly installed wheel in the Docker runtime.
- Persistent Redis and artifacts in Compose, health endpoints, and restart-persistence checks.
- Fixed-workload benchmarks for NumPy, threads, processes, Numba, and JAX; separate warmup, correctness validation, median/p95, runtime and GIL metadata.
- Numerical equivalence was verified locally for all five backends on CPython 3.12 and for NumPy/threads/processes on CPython 3.14t with the GIL disabled. These are workload-specific measurements.

## Validation and release assets

The implementation includes scientific reference, strict HTTP contract, Redis recovery, stale-worker artifact isolation, MLflow, tracing, research-pipeline, and benchmark tests. CI validates Python 3.12, 3.13, and 3.14, installed-wheel imports, and Docker restart persistence.

The GitHub release workflow builds and attaches the wheel, source distribution, and `SHA256SUMS` after successful CI for the exact protected-main commit. Existing published releases and tags are never moved or overwritten.
