# Архитектура и научные ограничения

## Границы компонентов

```text
HTTP → Pydantic-контракт → очередь → сервис → NumPy / Numba
                            │          ├─ артефакты запуска
                            │          └─ ExperimentTracker → MLflow (optional)
                            └─ статусы: память или Redis
```

`models/` содержит вычислительные типы и алгоритм без зависимости от HTTP, FastAPI, Pydantic или MLflow. `schemas/` задаёт транспортные контракты. Сервис переводит запрос в параметры модели, сохраняет результаты и вызывает порт `ExperimentTracker`. API получает ресурсы приложения через зависимости. Ресурсы создаются в lifespan и освобождаются при завершении; повторный запуск приложения в том же процессе создаёт новый комплект ресурсов.

Такое разделение позволяет использовать модель из тестов, CLI исследования и HTTP без копирования алгоритма. Для небольшого сервиса важнее эти проверяемые границы, чем количество слоёв DDD.

`EXECUTION_MODE` определяет размещение этих компонентов. `embedded` по умолчанию объединяет HTTP и отдельные ограниченные пулы симуляций, верификации и LJ research, допускает память или Redis. `api` обслуживает HTTP без потребителей этих очередей. Роль `worker` запускается через `python -m scientific_api.worker` и потребляет только симуляции; `verification-worker` — через `python -m scientific_api.verification_worker` и потребляет только проверки; `research-worker` — через `python -m scientific_api.research_worker` и потребляет только исследовательские анализы. Самостоятельные процессы не обслуживают HTTP. Все четыре раздельные роли требуют Redis: независимый процесс с собственной очередью в памяти не сможет получить задания API. Физика моделей остаётся прежней. Прежний анализ сохранённых скоростей OU продолжает выполняться синхронно в отдельном ограниченном пуле API.

## Модель `ideal-gas-ou-v1`

Для каждой из двух компонент скорости независимой частицы выполняется точный переход процесса Орнштейна — Уленбека:

\[
v_{n+1}=e^{-\Delta t}v_n+\sqrt{T(1-e^{-2\Delta t})}\,\xi_n,
\qquad \xi_n\sim\mathcal{N}(0,1).
\]

Коэффициент трения равен 1. Начальные компоненты скорости распределены как `Normal(0, T)`, поэтому распределение стационарно при заданной температуре. Точный переход устраняет зависимый от шага систематический нагрев прежнего случайного блуждания. Это термостатированная система: кинетическая энергия отдельной реализации не сохраняется.

Единицы приведённые, безразмерные: масса и постоянная Больцмана равны 1. Поле `initial_temperature` также задаёт температуру термостата; название сохранено в контракте API. Для `N` частиц:

\[
E=\frac12\sum_{i=1}^{N}\|v_i\|^2,\qquad
\widehat T=E/N,\qquad
\mathbb E[\widehat T]=T,\qquad
\operatorname{SE}(\widehat T)=T/\sqrt N.
\]

Стандартная ошибка описывает один конечный снимок, а не оценку по независимым моментам времени: соседние состояния коррелированы. В модели отсутствуют координаты, межчастичные силы, столкновения и физическая калибровка единиц. Она не заменяет проверенный пакет молекулярной динамики.

На входе проверяются конечность чисел, строгие типы, диапазоны и бюджет `num_particles * num_steps`. Неизвестные поля отклоняются. Ядро отдельно проверяет параметры и конечность результата, чтобы его безопасно вызывать вне API. Численная ошибка переводит задание в `failed`; некорректное число не должно становиться успешным JSON-значением `null`.

## Модель `langevin-free-v1`: координаты и перенос

Новая модель описывает независимые двумерные частицы с координатами и скоростями в приведённых единицах `k_B = 1`:

\[
dx=v\,dt,\qquad
dv=(-\gamma v+a)\,dt+\sqrt{2\gamma T_b/m}\,dW.
\]

`friction` — положительная скорость релаксации `γ`, а `acceleration` — постоянное внешнее ускорение `a`, уже делённое на массу. Масса, начальная температура `T_0` и температура ванны `T_b` задаются отдельно. Начальные координаты всех частиц равны `initial_position`; скорости имеют заданное среднее `initial_mean_velocity` и дисперсию каждой компоненты `T_0/m`. Поле изменяет средний поток, а не добавляет взаимодействие между частицами.

Координаты и скорости продвигаются совместным точным гауссовским переходом. При `E = exp(-γ Δt)`, `B = (1-E)/γ`, `C = (Δt-B)/γ`:

\[
v'=Ev+Ba+\eta_v,\qquad
x'=x+Bv+Ca+\eta_x.
\]

При `θ_b = T_b/m` шум одной компоненты удовлетворяет

\[
\operatorname{Var}(\eta_v)=\theta_b(1-E^2),\quad
\operatorname{Cov}(\eta_x,\eta_v)=\theta_b(1-E)^2/\gamma,
\]

\[
\operatorname{Var}(\eta_x)=\frac{\theta_b}{\gamma^2}
\left(2\gamma\Delta t-3+4E-E^2\right).
\]

Коррелированные шумы координат и скоростей важны для правильного MSD. При малом `γ Δt` коэффициенты вычисляются устойчиво через `expm1` и ряды. Присоединение `x += v*dt` к точному OU-шагу скорости не используется. Обе CPU-реализации используют одинаковые PCG64-приращения; `sample_stride` не меняет последовательность физических переходов или RNG.

### Границы и сохранение траектории

`unbounded` оставляет пространство неограниченным. При `periodic` задаются два размера бокса; физическое состояние и сохранённая траектория содержат непрерывные `unwrapped_positions`. Обёрнутый `positions = unwrapped_positions mod box_size` нужен для конечного представления внутри бокса. MSD считается по непрерывным координатам: скачок через границу не превращается в большое обратное перемещение и не создаёт ложного насыщения.

Сохраняются шаг `0`, кратные `sample_stride` и конечный шаг ровно один раз. Проверки до приёма ограничивают `N × steps`, число кадров до `1001` и массив координат `(frames, N, 2)` float64 до `64 MiB`. Этот бюджет относится к координатам траектории; полная память worker дополнительно включает текущее состояние, шум, анализ, сжатие и другие задачи. Число workers выбирается с учётом этих расходов.

### MSD и оценка диффузии

Для смещения `r_i(t)=x_i(t)-x_i(0)` сохраняются среднее смещение, полное `MSD = mean(|r_i|²)` и несмещённая оценка центрированного MSD `sum(|r_i-mean(r)|²)/(N-1)`. Полное MSD включает дрейф; центрированное описывает флуктуации относительно общего потока. Эти величины имеют разную нормировку при конечном `N` и явно различаются в отчёте.

При равновесных начальных скоростях, нулевом среднем и без поля аналитический эталон в 2D:

\[
D=\frac{T_b}{m\gamma},\qquad
\operatorname{MSD}(t)=4D\left[t-\frac{1-e^{-\gamma t}}{\gamma}\right].
\]

При малом времени это баллистическое движение `2(T_b/m)t²`; при большом — диффузионный рост с наклоном `4D`. В общем случае среднее смещение равно `B(t) μ_0 + C(t) a`, а дисперсия каждой компоненты координат — `2D[t-B(t)] + [(T_0-T_b)/m]B(t)²`. Теоретическое полное MSD дополнительно включает квадрат среднего смещения.

Оценка `D` — наклон OLS центрированного MSD по времени с независимым свободным членом, делённый на `4`. Окно задаётся шагами или выбирается автоматически из сохранённых кадров. Нужно не менее трёх точек и затухание переходного процесса: минимум пять времён релаксации, с более поздней границей при большом различии `T_0` и `T_b`. Также проверяется относительное смещение того же конечного окна на аналитическом MSD: оно должно быть не больше `1%`. Иначе расчёт сохраняется, а `diffusion.status` сообщает недоступную оценку с причиной.

Временные кадры одной частицы коррелированы. Поэтому стандартная ошибка подгонки не выводится из предположения независимых OLS-остатков: используется delete-one-particle jackknife, каждый раз исключающий целую траекторию частицы. Такая ошибка относится к конечной выборке независимых частиц, не включает остаточное смещение конечного окна и ошибку физической модели и не объявляется доверительным интервалом. Конечная шумная оценка наклона может оказаться отрицательной; она не заменяется нулём.

### Температура, энергия и артефакты

`kinetic_energy = (m/2) sum(|v_i|²)` включает поток. `thermal_temperature = m sum(|v_i-mean(v)|²)/(2(N-1))` оценивает тепловые флуктуации без смещения от среднего потока. Для этой модели ожидаемая температура скоростей равна `T_v(t)=T_b+(T_0-T_b)exp(-2γt)`; теоретическая стандартная ошибка данного оценивателя — `T_v(t)/sqrt(N-1)`. Формула старой модели `T/sqrt(N)` сюда автоматически не переносится.

Артефакты попытки: `final_state.npz` с координатами и скоростями, `trajectory.npz` с непрерывными координатами и временами, `transport.json` с наблюдаемыми и методикой, а также `manifest.json` с входами и SHA256 всех исходных файлов. Траектория допускает повторный анализ без повторного вычисления физики. Анализ Гаусса/Рэлея прежнего endpoint остаётся привязан к `ideal-gas-ou-v1` и не выдаёт поток нового режима за равновесное распределение с нулевым средним.

Периодическая область с постоянным ускорением описывает вынужденный дрейф. Стенки, оседание с барометрическим профилем, кулоновские силы, столкновения и потенциал Леннарда — Джонса в эту модель не входят. Её коэффициент диффузии зависит от заданного термостата и не является универсальным значением для реального вещества.

## Модель `lennard-jones-2d-v1`: парные взаимодействия

Частицы одинаковой массы движутся в двумерном периодическом прямоугольнике. Минимальный образ использует `r_ij = x_i-x_j-L*round((x_i-x_j)/L)`; для cutoff и skin требуется `r_c + skin < min(L)/2`. Начальная решётка исключает перекрытия. Gaussian-направления скоростей создаёт локальный PCG64, затем вычитается скорость центра масс и устанавливается заданная кинетическая температура. Такое состояние имеет фиксированную энергию скоростей и не является канонической выборкой.

Внутри cutoff применяются согласованные shifted-force потенциал и радиальная сила:

```text
U(r) = 4 epsilon [(sigma/r)^12 - (sigma/r)^6]
F(r) = 24 epsilon/r [2(sigma/r)^12 - (sigma/r)^6]
U_sf(r) = U(r) - U(r_c) + (r-r_c) F(r_c)
F_sf(r) = F(r) - F(r_c)
```

При `r >= r_c` энергия и сила равны нулю. Сила на пару равна `F_sf(r) r_ij/r`, а противоположная сила действует на вторую частицу. Обе величины непрерывны на cutoff. Минимум исходного LJ находится при `2^(1/6) sigma`, но shifted-force меняет положение минимума: при проверке нулевой силы нужно использовать минимум именно усечённого потенциала. Слишком тесное сближение приводит к явной ошибке, без скрытого смягчения сингулярности.

NVE продвигается velocity Verlet: половина импульса, полный дрейф координат, новая сила, вторая половина импульса. NVT использует BAOAB: половина силового импульса, половина дрейфа, точный OU-термостат скоростей, половина дрейфа и новая половина импульса. Точность OU-подшага не делает весь шаг с нелинейными LJ-силами точным. Уменьшение `dt` проверяется по сходимости энергии NVE и статистики NVT; шаг ограничен относительно `sigma*sqrt(mass/epsilon)`.

### Эталон и список соседей

`interaction_backend="direct"` проверяет все уникальные пары. `"verlet"` строит канонически упорядоченные пары через разреженные периодические ячейки в радиусе `r_c+skin`. Соседние ячейки и пары дедуплицируются, в том числе при малом числе ячеек. Пока смещение каждой частицы от позиции построения меньше `skin/2`, все действующие пары остаются в списке. Проверка использует непрерывные координаты: пересечение границы бокса не маскирует движение. Перед следующей оценкой силы список перестраивается при достижении границы.

Поле `backend` отдельно выбирает NumPy или Numba для арифметики. Версия физической модели и политика cutoff сохраняются. Numba подключается явно, работает с float64, `fastmath=False`, без внутреннего параллельного пула; отказ не заменяется другим backend. При одинаковых входных состояниях силы, энергия и virial сравниваются с прямым эталоном. Короткие траектории проверяются с численным допуском; хаотическая динамика не даёт основания обещать близость длинных траекторий при разном округлении.

### Наблюдаемые и неопределённость

Тепловая температура определяется относительно среднего потока: `T = m sum(|v_i-mean(v)|²)/(2(N-1))`. Кинетическая энергия `K=m sum(|v_i|²)/2` включает весь поток; `U=sum(U_sf)` и `E=K+U` могут быть отрицательными. Virial `W=sum(r_ij dot F_ij)` даёт механическое давление `P=(2K+W)/(2A)`, где `A=Lx*Ly`. Давление также знаковое. Аналитические ошибки температуры независимой OU-модели и `D=T/(m gamma)` к взаимодействующим частицам не переносятся.

`observables.json` хранит ряды этих величин, диагностику изменения энергии и конечный RDF. Для NVE энергия должна сходиться при уменьшении шага; нормировка ошибки использует `max(abs(E_initial), epsilon*N)`, чтобы начальная энергия около нуля не создавала искусственного деления. Для NVT изменение полной энергии отражает обмен с термостатом и не называется ошибкой сохранения энергии.

RDF конечного снимка использует двумерную площадь кольца `pi*(r_right²-r_left²)` при `r <= min(L)/2` и конечное число уникальных пар `N(N-1)/2`. Это описательная оценка одного снимка. Арифметические средние сохранённых кадров и выборочные SD после заданного `equilibration_steps` не включают SEM: кадры коррелированы, а удаление отдельных взаимодействующих частиц не является jackknife по независимым репликам. Неполный последний интервал не делает среднее взвешенным по времени. Наличие указанного burn-in не доказывает равновесие; межповторные SD/SE оцениваются отдельно по независимым seed.

Независимая NVT-проверка сопоставляет BAOAB-реплики с четырёхмерной конфигурационной квадратурой трёх частиц в периодическом боксе при совпадающих `T`, размерности и shifted-force cutoff. Разрешения сетки и отдельные допуски дискретизации хранятся в `tests/reference/lj2d_canonical.json`. В сочетании с проверками силы и сходимости NVE это проверяет нелинейный взаимодействующий случай, сохраняя явно ограниченную область вывода.

### Ресурсы и артефакты

Число частиц ограничено `4096`, работа — `N*steps <= 20_000_000`. Для прямого варианта до приёма учитываются начальная сила, силы всех шагов и конечный RDF: `(steps+2)*N*(N-1)/2 <= 100_000_000`. Во время исполнения также ограничиваются проверки пар сил, построения соседей и RDF. Диагностика показывает фактические счётчики и число перестроений; достижение бюджета даёт явную ошибку вместо неограниченного вычисления.

Непрерывная координатная траектория ограничена `64 MiB` и `1001` кадром. Ансамбль дополнительно ограничивает суммарную траекторию `512 MiB` и суммарную работу соответствующего алгоритма. Эти величины не оценивают весь RSS процесса или дисковый объём всех ранее завершённых исследований.

Подтверждённая попытка сохраняет `final_state.npz` с координатами/скоростями, `trajectory.npz` с непрерывными координатами и временем, `observables.json` и manifest с параметрами, интегратором, cutoff, RNG, диагностикой, окружением и хешами. Постоянное поле и невзаимодействующая теория переноса остаются отдельным контрактом `langevin-free-v1`. LJ-модель задаёт проверяемый вычислительный пример; интерпретация как конкретной жидкости требует согласованных единиц, размерности, плотности, cutoff, термостата и независимой валидации.

## Вычислительный backend

Параметр `backend` допускает только `numpy` и `numba`; NumPy используется по умолчанию. Фабрики `models/computation.py`, `models/langevin_engine.py` и `models/lennard_jones_engine.py` выбирают реализацию соответствующей модели из фиксированного набора без пользовательских import path. Интерфейс ядра отделяет продвижение на один шаг `advance()`, чтение состояния и `execution_metadata()` от HTTP, Redis, tracking и сохранения файлов. Прежний `IdealGasSimulator` дополнительно сохраняет `observables()` и публичный `step()`. Выбор backend не меняет физическую модель или её версию.

В обеих реализациях начальное состояние и каждый массив шума создаёт локальный NumPy PCG64. Это сохраняет правило сопоставления seed последовательности случайных приращений; Numba не использует собственный RNG. Состояние ядра и шум одного шага имеют память порядка числа частиц: полный массив шума на все шаги не создаётся. Сохраняемая траектория новой модели имеет отдельный бюджет по числу кадров и частиц. NumPy остаётся эталоном для численной проверки. Повтор в фиксированном backend и окружении проверяется отдельно от межbackend-сравнения с допуском; побитовое совпадение на произвольных платформах не обещается.

Numba загружается только при явном исполнении с `backend="numba"`; проверка отсутствующего extra при приёме не импортирует и не компилирует Numba в HTTP-процессе. В минимальной установке API и NumPy работают без Numba и JAX. Если Numba отсутствует, API возвращает `503` до приёма; если её импорт или компиляция не удаются на worker, задание завершается ошибкой, без подмены реализации. Окружения API и всех потребителей одной очереди должны поддерживать принимаемый backend; маршрутизации заданий по возможностям worker пока нет.

Ядро Numba — последовательное CPU-обновление float64 с `nogil=True`, `fastmath=False`, без внутреннего пула потоков. Параллелизм между заданиями по-прежнему ограничен `WORKER_COUNT` и числом процессов. Дисковый кеш отключён: первая работа в процессе оплачивает импорт и компиляцию. Сервис выполняет наблюдаемые в конечном состоянии вместо лишней редукции на каждом шаге, сохраняя кооперативную отмену и публикацию прогресса между шагами. Последний вычислительный шаг по-прежнему предшествует сохранению артефактов и подтверждению результата.

Выбранный backend сохраняется в payload, включая дочерние задания ансамбля, и не меняется при повторной доставке. Отсутствующее поле в сохранённом старом payload означает NumPy. Manifest `execution` фиксирует фактический backend, версии реализации и ядра, устройство, dtype, параметры вычисления и RNG policy. JAX остаётся экспериментом benchmark: API не принимает `backend="jax"`, не выбирает GPU автоматически и не обещает ускорения без измерений на подтверждённом устройстве.

## Задания и жизненный цикл

Один `task_id` создаётся при приёме запроса и используется во всех статусах, артефактах и tracking. `pending` сохраняется до ответа `202`; после извлечения из очереди задание становится `running`, затем `completed` или `failed`. Публичный `POST /simulations/{task_id}/cancel` подтверждает запрос отмены ответом `202`; это ещё не подтверждение остановки работающего вычислителя. Отмена кооперативная, окончательное состояние доступно через прежний polling и SSE.

Вычисление выполняется вне цикла событий HTTP. `WORKER_COUNT` ограничивает число вычислителей **в каждом процессе** embedded/worker, `MAX_QUEUE_SIZE` — число принятых незавершённых заданий, включая исполняемые. Превышение ёмкости приводит к отказу в приёме, а не к неограниченному росту памяти. Остановка прекращает приём и инициирует кооперативное завершение работы. Самостоятельный worker обрабатывает SIGTERM и завершается при неожиданном отказе своего цикла. Число процессов и их перезапуск контролирует развёртывание; это не общий GPU-планировщик.

В роли `api` готовность HTTP зависит от backend, а потребители очереди симуляций не создаются. Поэтому успешный `/health/ready` API не доказывает наличие активных workers. У отдельного worker нет HTTP health endpoint; нужны наблюдение за процессом и политикой его перезапуска. В Compose override отключена унаследованная от API HTTP-проверка контейнера worker.

По умолчанию очередь и статусы находятся в памяти. Этот режим поддерживает **один процесс сервера**, не переживает перезапуск и подходит для локальной разработки.

При `REDIS_URI` используются общие статусы и очередь Redis с подтверждением обработки, арендой задания и восстановлением работы после истечения аренды. Семантика доставки — **как минимум один раз**: после сбоя вычисление может повториться, поэтому постоянный task ID, детерминированный seed и контроль записи результата важны. Число попыток ограничено. Это не гарантия «ровно один раз» для внешних побочных эффектов, например независимых записей в стороннюю tracking-систему. Операционную политику хранения Redis, резервного копирования и отказоустойчивости задаёт развёртывание.

По умолчанию checkpoint отключён и восстановление после потери аренды начинает новую попытку с исходных параметров и seed. При включённом сохранении новая попытка получает последний зарегистрированный checkpoint отдельно от физического payload. Progress старой попытки не является позицией для продолжения; учитывается только подтверждённый дескриптор состояния.

Переход с протокола до SSE/ансамблей требует остановки всех старых embedded API/workers перед приёмом ансамблей новым API в том же Redis namespace. Старый `finish` не публикует родительские вклады и не обрабатывает новый протокол отмены, поэтому смешанное исполнение не поддерживается. Сохранённые старые записи и payload читаются новой версией после остановки старых consumers. Порядок drain/stop с сохранением Redis/артефактных томов и вариант отдельного namespace приведены в [руководстве по разработке](development.md).

При обновлении до выбора backend также остановите старые consumers: предыдущая версия не принимает новое поле `backend` в параметрах задания. Сначала обновите все процессы, затем возобновляйте приём. Само добавление Numba не требует удаления Redis или файлов результатов.

При включении `langevin-free-v1` действует такое же требование: прежний worker не знает новый тип модели и её результат. Payload новой модели содержит явный `model`; сохранённый старый payload без этого поля продолжает означать `ideal-gas-ou-v1`. Обновите всех потребителей общей очереди до одной версии и сохраните прежние Redis/artifact volumes.

Перед приёмом `lennard-jones-2d-v1` также обновите все consumers общей очереди: предыдущие версии не знают этот model/result. Развёртывайте согласованную проверенную версию API и workers.

Каждое исполнение API-задания получает отдельный UUID `attempt_id` и каталог `ARTIFACTS_DIR/<task_id>/<attempt_id>/`. Завершённый статус публикуется только для текущего владельца задания и содержит пути его попытки. Поэтому запоздалый вычислитель с истёкшей арендой не перезаписывает файлы принятого результата. Скачивание по публичному URL с `task_id` выбирает артефакты из подтверждённого статуса, а не из произвольной папки попытки. Исследовательский CLI вызывает сервис напрямую без очереди и сохраняет детерминированную структуру без дополнительного UUID.

TTL статуса ограничивает срок его доступности; истёкший ID возвращает `404`. Артефакты имеют отдельный жизненный цикл. При нескольких хостах нужен общий каталог или объектное хранилище артефактов. Redis не синхронизирует файлы.

## Прогресс и SSE

`GET /simulations/{task_id}/events` предоставляет ограниченную историю событий и текущие обновления через SSE. Владение арендой ограничивает публикацию progress: запоздавший вычислитель не может менять прогресс или результат новой попытки. Счётчик `attempt` позволяет клиенту отделить новый запуск от прежнего; UUID `attempt_id` остаётся идентификатором подтверждённого результата. Общий статус задания сохраняет прежний контракт.

Клиент возобновляет поток с `Last-Event-ID`. Журнал ограничен последними 256 событиями, а число одновременно открытых соединений — настройкой `SSE_MAX_CONNECTIONS`. При недоступном cursor требуется принять `reset` и актуальный снимок, а не считать историю полной. SSE облегчает наблюдение, но не служит постоянным журналом исследования и не гарантирует однократную доставку клиенту. Polling остаётся способом получить текущее состояние после разрыва или истечения истории.

## Ансамбли независимых повторов

Ансамбль задаёт одну модель и набор параметров без seed, число повторов `1..50`, базовый seed и политику `require_all`. До начала вычислений сохраняются идентификаторы дочерних заданий и их seed. Приём атомарно резервирует ёмкость очереди для всех повторов; недостаток ёмкости не должен оставлять частично принятый ансамбль. Суммарный бюджет учитывает `replicas * num_particles * num_steps`, а 50 повторов не создают 50 отдельных потоков: их забирают существующие workers.

Родительская запись хранит подтверждённые вклады дочерних заданий с task/attempt ID, а не собирает агрегат только из временных статусов при каждом GET. Пока доступна родительская запись, уже сохранённый вклад переживает истечение TTL статуса ребёнка. Доступ к файлам отдельного задания и их очистка всё равно имеют собственные ограничения.

Среднее и неопределённость относятся к независимым повторным расчётам. При `require_all` ошибки и отмены не выдаются за успешно завершённую выборку. Выборочное стандартное отклонение использует `ddof=1`, а стандартная ошибка среднего — SD/√M; обе определены только при как минимум двух успешно завершённых повторах всего ансамбля. Один повтор не даёт оценки межповторной дисперсии. Это другой уровень неопределённости, чем теоретическая ошибка температуры одного снимка `T/√N`.

Модель определяет состав агрегатов. У `langevin-free-v1` это тепловая температура, кинетическая энергия и конечное центрированное MSD; оценки диффузии агрегируются только при доступной оценке во всех успешных репликах. Теоретическая ошибка среднего тепловой температуры равна `T_v(t)/sqrt((N-1)M)`. Межповторная SD/SE отличается от jackknife-ошибки отдельной оценки диффузии. При приёме дополнительно проверяется суммарный объём несжатых координат всех траекторий ансамбля — не больше `512 MiB`; это бюджет данных, а не оценка одновременной памяти процессов или сжатого архива.

Необязательный `Idempotency-Key` защищает повтор приёма ансамбля: одинаковый ключ и запрос возвращают тот же ID, конфликт параметров — `409`. Ключ не превращает внешние побочные эффекты выполнения в «ровно один раз». Терминальный manifest фиксирует семена, статусы и происхождение вкладов; он необходим для проверки агрегата.

Анализ скоростей отдельного снимка остаётся синхронной ограниченной потоковой операцией с ответом `201`. Наличие очереди ансамблей и SSE не меняет его в постоянную очередь анализов и не добавляет ему идемпотентность.

## Воспроизводимость и provenance

Каждый запуск создаёт локальный `numpy.random.Generator(PCG64(seed))`. Manifest связывает параметры, версию модели, алгоритм RNG, итоговые метрики, версии Python/пакетов и доступные сведения о checkout/оборудовании. `final_state.npz` хранит конечные скорости для независимого пересчёта метрик. Commit может отсутствовать в установленном wheel; manifest должен отражать отсутствие, а не выдумывать значение.

Одинаковые seed и окружение позволяют проверить воспроизводимость; совпадение между разными версиями NumPy, CPU или backend отдельно не обещается. Lockfile фиксирует зависимости, но не весь образ ОС, драйверы и оборудование. Публикуемый результат должен включать manifest, исходные артефакты и сведения об окружении.

## Контракты и конверт результата

Фиксированный диспетчер моделей дополнен каталогом `ModelContract`. Каталог связывает текущие transport-схемы с единицами, допущениями, инвариантами, диагностикой, политикой версии и обязательными артефактами. Он не принимает пользовательский код и не создаёт динамическую систему plugins. Доступность backend отделена от контракта: локальное обнаружение пакета не означает готовность независимого worker. Контракт имеет свой digest; версия модели и digest реализации остаются отдельными идентификаторами. Конверт сохраняет собственный снимок контракта и проверяет его digest независимо от последующих изменений каталога.

Штатная публикация нового результата выполняется в порядке «артефакты → manifest → Result Envelope → подтверждение задачи». Manifest сохраняет прежний `outputs` и содержит объявление расположения `envelope.json`. Конверт ссылается на digest точных байтов manifest и файлов; обратной ссылки с digest нет. Это позволяет сохранять старые ответы API без циклического хеширования. При создании анализа конверт записывается после переноса его каталога в конечное расположение, но до возврата `201`. Ошибка публикации до попытки архивирования удаляет только что созданный каталог анализа. После попытки записи в архив неопределённый исход, например потеря Redis acknowledgment, требует сохранения полных файлов: запись могла подтвердиться. Такой запрос возвращает `503`, а успешную регистрацию можно обнаружить через происхождение исходной задачи; автоматической фиктивной отмены записи нет. Конверт сохраняет связь с подтверждённой исходной попыткой.

Перед подтверждением worker проверяет обязательные доказательства целостности; endpoint конверта повторяет проверку по текущим байтам. Отсутствие не объявленного исторического конверта возвращается как `not_verified`, а объявленный, но отсутствующий или несогласованный конверт приводит к конфликту. Проверка не импортирует Numba, plotting или tracking extras и не вычисляет физику повторно.

`verified` в Result Envelope относится к согласованности с сохранёнными метаданными. Это не цифровая подпись и не результат отдельного verification worker. Хранилище артефактов и архив происхождения остаются доверенными частями развёртывания; злоумышленник с правом согласованной перезаписи всех метаданных не ограничивается SHA256. Runtime-проверки и условные оценки неопределённости публикуются отдельно; подписанные свидетельства не добавляются этими механизмами.

## Архив происхождения и журнал жизненного цикла

Оперативные записи очереди и bounded SSE остаются прежними. Отдельный архив содержит исходный payload, фактические попытки и терминальный результат, ссылки на конверт и зарегистрированные анализы. Redis хранит archive hash и lifecycle stream без TTL/MAXLEN; Lua-операции меняют архив и очередь атомарно. Числовые payload/result JSON сохраняются без перекодирования через Lua, чтобы не потерять точность `uint64` seed. Память реализует тот же интерфейс, но не обеспечивает долговременность после перезапуска процесса.

В журнал попадают submit, claim, retry/release, cancel request, фактическое завершение и анализ. Он не получает heartbeat или каждый физический шаг. Архивный task ID не освобождается после истечения live TTL: новая задача не может присвоить чужое происхождение. Журнал растёт; retention, резервное копирование и допустимый объём задаются оператором отдельно от `TASK_TTL_SECONDS`.

Для одной OU-задачи архив ограничен `256` зарегистрированными анализами сохранённых скоростей: предварительная проверка перед вычислением и атомарная проверка при записи предотвращают неограниченный рост и гонки. Достигнутый предел даёт постоянный `429 ANALYSIS_ARCHIVE_LIMIT_EXCEEDED` без `Retry-After`; существующий analysis ID можно повторно зарегистрировать идемпотентно. Отдельные verification и LJ research отчёты используют собственные индексы и пределы. Граф и сериализованный ответ дополнительно ограничены `4096` узлами и `16 MiB`.

Owner fencing распространяется на архивирование доказательств: устаревший owner не публикует победившие артефакты. Сохранённая отмена может заменить запрошенный успешный исход, и тогда архив фиксирует отмену, без индекса не подтверждённых файлов. Для нового анализа архивная запись создаётся до успешного ответа `201`. Частично доступная история старых задач явно отмечается наблюдением, без реконструирования не записанных событий.

`ProvenanceService` получает историю из архива независимо от live TTL. Перед выдачей подтверждённой цепочки он повторно проверяет конверт и его связь с сохранённым digest manifest. Стабильный ID артефакта идентифицирует его происхождение (`task_id`, `attempt_id`, `analysis_id`, имя), а SHA256 байтов хранится отдельно. Это позволяет различать одинаковые данные разных запусков без смешивания их происхождения.

Граф JSON-LD использует W3C PROV для связей вычисления и данных. Экспорт generic RO-Crate 1.1 собирает ограниченный ZIP только из проверенных подтверждённых файлов, метаданных и анализов. Он не присваивает результатам лицензию исходного кода и не создаёт PID или подтверждённую человеческую идентичность. Журнал Redis требует AOF и сохранённых томов; он не заменяет резервную копию файлов. История метаданных не является checkpoint или точным состоянием физики на произвольный момент.

## Детерминированный checkpoint и продолжение

`CheckpointControl` координирует сохранение в сервисе без изменения физического запроса. `CHECKPOINT_INTERVAL_STEPS=0` отключает создание checkpoint; положительное значение задаёт желаемую частоту. Адаптивный интервал ограничивает число зарегистрированных состояний до `32` и суммарный объём до `512 MiB` на логическую задачу, включая начальную и конечную границы. Checkpoint сохраняется после полного шага и выборки, а конечный LJ checkpoint — до резервирования terminal RDF work.

Версионированный JSON и NPZ содержат только разрешённые поля: PCG64, координаты и скорости, модельные coefficients/caches, накопленные префиксы выборок и cursor. Для LJ сохраняются cached force/U/virial, Verlet reference/pairs и расход парных бюджетов. Восстановление не вызывает случайную инициализацию, не вычисляет начальные силы повторно и не обнуляет рабочие счётчики. Загрузка проверяет размер, hash, shape/dtype, конечность и state ABI без pickle.

Сначала файлы атомарно публикуются в неизменяемом checkpoint-каталоге, затем текущий owner регистрирует дескриптор через операцию backend с проверкой lease. Не подтверждённые каталоги не сканируются для восстановления. При retry/shutdown продолжение читает только последний зарегистрированный дескриптор. Он передаётся в `Job.checkpoint` отдельно от исходного payload, сохраняя старые контракт и идемпотентность ансамблей. Потерявший owner не может заменить выбранное состояние.

Fingerprint связывает state ABI и релевантные физические модули с Python/NumPy/backend/LLVM, CPU/libc и float64/RNG policy. Общий commit, dirty-флаг и изменения документации/API не используются как самостоятельный критерий совместимости. Неизвестная совместимость не выдаётся за успешную: повреждение и конфликт окружения имеют отдельные коды, без скрытого старта с seed. Окончательную проверку всегда выполняет worker, поскольку роль API не описывает аппаратную среду других consumers.

Ручное resume сохраняет `task_id` и параметры, но открывает новую попытку только для failed/cancelled самостоятельной задачи. Существующий completed результат и дети ансамблей не переоткрываются. Повтор того же активного продолжения идемпотентен; допустимо до `32` ручных продолжений. Provenance связывает исходную попытку, checkpoint, шаг и новую попытку. Гарантия точности относится к научным массивам/выборкам/наблюдаемым и LJ counters при поддерживаемом окружении, а не к UUID, timestamps или байтам упаковки. Существующий RO-Crate экспорт включает ссылки происхождения, но checkpoint state скачивается отдельно.

## Отдельный контур верификации

`VerificationManager` использует отдельные `MemoryVerificationStore`/`RedisVerificationStore`, bounded thread pool и leased delivery. Redis-очередь находится в отдельном namespace; её задания, попытки и терминальные сертификаты не перезаписывают очередь симуляций, source archive или научные файлы. Доставка как минимум один раз допускает повтор после сбоя; owner fencing разрешает зафиксировать терминальный отчёт только текущему владельцу. Неоднозначное подтверждение записи не заменяется новой ошибкой: подтверждённый отчёт остаётся неизменным, а неподтверждённую попытку восстанавливает аренда.

Приём требует архивный completed source с evidence и сохраняет точные идентификаторы и digests. Проверяющий получает снимок через no-follow чтение ограниченных файлов: именно проверенные байты поступают в независимый численный анализ. Существующий конверт проверяет целостность; отдельная реализация пересчитывает поддерживаемые наблюдаемые и инварианты. По запросу добавляется ограниченный same-seed rerun в собственном временном каталоге. Это не новые образцы независимой статистики и не право менять входы или выбирать скрытый backend.

Состояние задания отделено от вердикта. Готовый сертификат может содержать `failed`, `inconclusive` или `unsupported`; `completed` не равен научному успеху. Сертификат фиксирует policy, source anchor, отдельный verifier attempt, проверки с причинами и ограничениями, реализацию/окружение и время проверки. Канонический JSON хранится в терминальной записи с SHA256. GET проверяет собственный digest свидетельства независимо от сегодняшних source bytes. Это историческое unsigned evidence, не цифровая подпись, не доказательство авторства и не универсальная валидация модели.

Список проверок источника ведётся только в verification store; исходные Result Envelope, provenance graph и RO-Crate не изменяются. Это исключает двойную запись между независимыми хранилищами. Наличие поздней проверки не меняет исходный `scientific_verification="not_performed"`: потребитель отдельно читает verification records и их policy. Redis удерживает сертификаты после оперативного TTL; память теряет их при остановке процесса. Результат проверки не гарантирует неизменность исходных файлов в будущем.

`VERIFICATION_WORKER_COUNT` ограничивает проверяющих в каждом процессе (`1` по умолчанию), `MAX_VERIFICATION_QUEUE_SIZE` — незавершённые проверки в очереди (`32`). Предел источника — `32` сохранённые проверки; повтор POST использует новый слот. Общие `TASK_LEASE_SECONDS`/`MAX_TASK_ATTEMPTS` задают аренды/повторы. Rerun имеет отдельные пределы particle-steps и LJ pair checks. Embedded одновременно исполняет simulation и verification pools; раздельный запуск позволяет планировать их CPU и память независимо и требует согласованных версий/extras и доступа к исходным артефактам.

## Отдельная очередь LJ research

`ResearchManager` использует отдельный namespace и очередь с арендами/owner fencing, сохраняя неизменяемый JSON-отчёт с SHA256. Источники закрепляются по archive evidence и parameters; worker перечитывает проверенные байты. Отчёт не модифицирует физический payload, исходный snapshot uncertainty, Result Envelope, verification certificate, provenance graph или RO-Crate. Новые отчёты находятся через собственные URL и список primary anchor. Сохранённый отчёт описывает свой исходный снимок и не объявляет последующие изменения файлов невозможными.

Временной анализ использует только регулярные сохранённые кадры после production threshold/burn-in. Укороченный терминальный отсчёт исключается; несохранённые моменты не интерполируются. IAT имеет конвенцию `g>=1`, ESS — `n/g`. Основные SE/Student-t CI строятся по `8..50` длинным неперекрывающимся batch means, с `SE=SD(batch_means)*sqrt(block_length/n)` и центром по всем выбранным кадрам. Остаток неполного блока не участвует только в оценке дисперсии. IAT-based SE сохраняется отдельно, moving-block percentile bootstrap — только вторично и exploratory. Все интервалы условны на стационарности/представительности, разрешённой корреляции и приближённо Gaussian слабо зависимых batch means. Диагностические экраны и ACF-эвристика не доказывают равновесие, смешивание или отсутствие невидимых медленных мод; недоступные оценки имеют причины, а не нулевую ошибку.

Межрепличный анализ использует целые траектории как независимые единицы, строго согласованные параметры/окна и различные seed. Основной Student-t CI требует как минимум восьми приближённо нормальных независимых средних; secondary bootstrap остаётся exploratory. Чувствительность сравнивает согласованные seed-группы при изменении одного шага времени или cutoff: парные contrasts характеризуют наблюдаемые изменения, а не истинную ошибку предельного шага, бесконечного cutoff или модели. Подмножества выживших и дополнительные псевдореплики из отдельных частиц/кадров не создаются.

`RESEARCH_WORKER_COUNT=1` по умолчанию ограничивает consumers в каждом embedded/research-worker процессе; `MAX_RESEARCH_QUEUE_SIZE=16` ограничивает незавершённые задания. Используются прежние lease/max-attempt settings. На primary anchor допускается `32` сохранённых отчёта; вход ограничен `50` задачами, `512 MiB` исходных артефактов, а request/report — `1 MiB`. Число bootstrap draws и формат запроса дополнительно ограничены. Redis сохраняет отчёты после live TTL; память теряет их при остановке процесса.

Готовность очереди и доступность статистики независимы: completed research job может содержать частично или полностью недоступный интервал. Для report GET проверяется собственный canonical digest, без повторного физического или статистического вычисления. Научные модули используют только NumPy; Matplotlib, SciPy и notebook-инструменты не становятся зависимостями core. Прежний synchronous velocity-analysis контракт `201` сохраняется.

## Интеграции и наблюдаемость

Базовая установка не импортирует MLflow, Redis, Jupyter, OpenTelemetry, Numba или JAX. Соответствующий extra устанавливается перед включением адаптера. Tracking отключён при пустом URI; инфраструктурные ошибки должны быть видны в статусах, логах или телеметрии, а не маскироваться успешным подключением.

OpenTelemetry переносит контекст от HTTP к заданию и вычислению, включая прохождение очереди. Метрики ожидания, выполнения и ошибок позволяют отличать перегрузку очереди от медленного ядра. Число частиц и длительности полезны для агрегации; task ID и seed не следует превращать в метки метрик с неограниченной кардинальностью.

Публичное размещение требует собственных политик аутентификации, TLS, квот и сетевого доступа. Локальный Compose демонстрирует интеграции; он не подтверждает готовность к работе на HPC, GPU или в отказоустойчивом кластере.
